# ADR-004: The Manifest Schema Is Derived from the Manifest Types

## Status

Accepted

## Context

The manifest format is stated in one place: the Go types of `internal/infra/manifest`, together with the checks in `Repository.validate()` that the types cannot carry themselves. Which keys a document may hold, which values an enum accepts, which fields are required and which combinations are refused all live there.

That statement only fires once a command parses a file. `infra validate` reports an unknown key, a misspelled enum value or a missing field, and nothing reports them earlier. A document is written blind and its mistakes are learned by running something against it.

The documents are meant to be hand-edited. `infra import` exports a project as a manifest that an operator then commits and maintains, and [ADR-003](./adr-003-a-schedule-is-identified-by-its-description.md) made that export consequential: an exported `pipeline_schedules: []` declares that the project holds no schedule, so what the operator does to that document decides what apply removes. An editor that knew the rules could report the mistake while the line is being typed, and an editor learns rules from a JSON Schema.

A schema is therefore worth having, and there are two ways to get one. Writing it by hand produces a second, independent statement of the same format, which drifts from the first as soon as either changes and gives no sign that it has. Deriving it from the types produces one statement with two readers, and drift stops being possible for everything the type system carries: the field names, the enum values, the rejection of unknown keys, and simple required-ness.

Three rules are not carried by the type system and had to be handled individually. The allowed values of each enum were spelled out as inline arguments to `enumValue` inside `UnmarshalYAML`, reachable only by calling the decoder. The `apiVersion` and `kind` values are pinned by a probe that compares them against exported constants before the document is decoded, and a struct tag cannot name a constant. The rule that `description` is required when `ci_catalog` is true relates two sibling fields, which no Go type expresses.

One rule cannot be expressed in JSON Schema at all. [ADR-003](./adr-003-a-schedule-is-identified-by-its-description.md) makes a schedule's description its identity, so `validateSchedules` refuses a document that repeats one, and JSON Schema constrains items rather than one property across items. Whatever is derived is therefore a weaker check than the parser and can never become a substitute for it.

## Decision Drivers

- **A rule is stated once**: two statements of the same format drift apart, and the one an editor applies is the one nobody runs against a file.
- **An editor helps before a command is run**: the format is currently unknowable until a document is parsed, which is after it has been written.
- **A rule that must be stated twice is visible against the other statement**: restating one is survivable only if a change to either is read alongside the other.
- **The schema does not become the authority**: `infra validate` stays the check a document must pass, so a rule the schema cannot express is not a rule that disappears.

## Considered Options

### Option 1: Leave the rules in the parser alone

The Go types and `validate()` stay the only statement of the format, and a document is checked by running `infra validate`.

**Pros:**

- One statement of the format, so nothing can drift.
- Nothing is generated and nothing is committed that a change to the types could invalidate.

**Cons:**

- An exported manifest gets no completion and no validation while it is edited, which is where the mistakes are made.
- The rules are readable only as Go, so anyone asking what a manifest may contain reads the parser or the documentation about it.

### Option 2: Write a JSON Schema by hand

A schema is authored and committed as its own artefact, describing the same format the types describe.

**Pros:**

- Every rule JSON Schema can express is available, including ones no Go type carries, without a generator deciding what is emitted.
- The schema can be written for a reader rather than derived, so its titles and descriptions are chosen.

**Cons:**

- The format is stated twice in full, and nothing pairs the statements, so a field added to a type is simply missing from the schema until someone notices.
- The drift is silent in the harmful direction: an editor reporting a document clean against a stale schema is how a rejected document is written confidently.

### Option 3: Derive the schema from the types, restating only what cannot be derived

The schema is generated by reflecting over the manifest types, committed, and checked by a test. Rules the type system cannot carry are lifted onto the types where possible and written a second time where not.

**Pros:**

- Everything the types carry is stated once, and a change to a type reaches the schema through the test rather than through anyone remembering.
- The committed file is reviewable in a diff, so a change to a type shows what it did to the published format.
- The second statement is confined to the one rule that needs it, and its placement can be chosen.

**Cons:**

- The catalog prerequisite exists in two forms, and nothing checks that they agree.
- The generated shape is the library's, so a field's rendering is chosen by the reflector rather than by whoever wrote the type.

## Decision

We will derive the manifest's JSON Schema from the Go types, commit it, and state a rule a second time only where the type system cannot carry it.

### 1. The schema is generated from the types, and one test both writes and checks the committed file

**Change from**: the manifest format exists only as Go, and nothing outside the program can read it.

**Change to**: `manifest.Schema()` reflects `Repository` into a JSON Schema, which is committed at `schema/repository.schema.json`. `TestCommittedSchemaMatchesTypes` regenerates that file when run as `go test ./internal/infra/manifest/ -update`, and otherwise fails when the committed file differs from what the types produce.

**Rationale**: Deriving the schema is what makes drift impossible rather than merely discouraged. The file still has to be committed, because an editor fetches a schema rather than running a Go program, and a committed derived file is a copy that can go stale. Having the same test write it and check it is what closes that: the check cannot disagree with the generator, because the generator is what it compares against, and repairing a failure means running the test rather than editing JSON.

### 2. What the generator cannot see is lifted onto the types, pinned from the existing constants, or restated next to the rule it repeats

**Change from**: the enum values live inside `UnmarshalYAML`, the header constants are consulted only by the parse probe, and the catalog prerequisite exists solely in `validate()`.

**Change to**: each enum type owns an `allowedValues()` method that both `UnmarshalYAML` and a `JSONSchema()` method read, so the values decoding accepts and the values the schema lists are the same list. `Repository.JSONSchemaExtend` pins `apiVersion` and `kind` to the `APIVersion` and `KindRepository` constants the probe already compares against. `RepositorySpec.JSONSchemaExtend` states the catalog prerequisite a second time, as the `if`/`then` JSON Schema can express, and sits immediately below the `validate()` that states it first.

**Rationale**: Two of the three needed no second statement, only a way to be read without decoding, and lifting the enum values onto their types was done as a change of its own before anything consumed them. The third has no such route. The prerequisite relates `description` to `ci_catalog`, which no Go type expresses, so it is written twice and the duplication is the accepted cost of the rule reaching an editor at all. What makes it survivable is where it is: the two statements are adjacent, so a change to one is read against the other in the same diff.

The parser's statement is the one apply depends on:

```go
if repo.Spec.CICatalog != nil && *repo.Spec.CICatalog {
	if repo.Spec.Description == nil || *repo.Spec.Description == "" {
		return fmt.Errorf("%w: spec.description is required when spec.ci_catalog is true", errRequiredField)
	}
}
```

The schema's statement repeats it in the only form JSON Schema offers:

```go
func (RepositorySpec) JSONSchemaExtend(schema *jsonschema.Schema) {
	catalogRequested := &jsonschema.Schema{
		Properties: jsonschema.NewProperties(),
		Required:   []string{"ci_catalog"},
	}
	catalogRequested.Properties.Set("ci_catalog", &jsonschema.Schema{Const: true})
	schema.If = catalogRequested
	schema.Then = &jsonschema.Schema{Required: []string{fieldDescription}}
}
```

### 3. Every exported document names the schema of the revision that emitted it

**Change from**: `infra import` writes documents separated by `---`, and nothing in the output says where the rules for them live.

**Change to**: each emitted document is headed by a `yaml-language-server` modeline naming the committed schema, written again after every separator:

```text
# yaml-language-server: $schema=https://raw.githubusercontent.com/Omochice/nyctereutes/refs/tags/v1.2.3/schema/repository.schema.json
apiVersion: nyctereutes/v1
kind: Repository
```

The ref is `refs/tags/v` followed by the version stamped into the build at link time. An un-stamped build has no revision of its own and names `refs/heads/main` instead.

**Rationale**: A schema nothing points at is a schema nobody applies, and the export is exactly the document that arrives without an editor knowing what it is. The line is repeated per document because an editor reads it out of one document's own leading comments and does not carry it across a separator, so writing it once at the top of the stream would leave every document but the first unhelped. The ref is pinned because the rules an editor applies to a document should be the rules of the build that produced it; naming a moving branch would apply whatever `main` holds today to a document written against something else.

## Consequences

This record is carried out, so what follows describes how the tool behaves rather than what it would do.

### Positive

1. **The format is stated once for everything the types carry**: a field added to a type, an enum value added to an `allowedValues()`, or a `jsonschema:"required"` tag reaches the schema without anyone editing it, and the test refuses a commit that leaves the file behind.
2. **A change to the format is visible as a change to the published format**: the generated file is committed, so a diff shows what a change to a type did to what an editor will enforce.
3. **An exported manifest is editable with help**: an editor that reads the modeline completes the keys, offers the enum values and reports an unknown key, a wrong type or a missing required field while the document is being written.
4. **Header mistakes are reported the way the parser reports them**: `apiVersion` and `kind` are pinned to the constants the probe compares against, so a document for another tool or another version is refused by an editor rather than only by `infra validate`.
5. **A document names the rules it was written against**: an export from an older build sends an editor to that build's schema, so a rule added since is not applied to a document that predates it.

### Negative

1. **One rule is stated twice**: the catalog prerequisite exists in `validate()` and in `RepositorySpec.JSONSchemaExtend`, and nothing checks that the two agree, so changing one leaves the other stating the old rule silently.
2. **The schema is a weaker check than the parser**: the uniqueness of a schedule's description, which [ADR-003](./adr-003-a-schedule-is-identified-by-its-description.md) makes the identity every plan and apply rests on, cannot be expressed in JSON Schema and is not attempted, so an editor can report a document clean that `infra validate` refuses.
3. **An explicit null is flagged though the parser accepts it**: the optional spec fields are pointers and the reflector renders them as plain scalar types, so `description: null`, which decodes as the field being unset, is reported as a type error. Expressing it would mean a nullable union on every optional field.
4. **The lint configuration carries an exclusion for the generator's sake**: `recvcheck` is told to ignore `JSONSchema` and `JSONSchemaExtend`, because the library looks them up on the value type while the decoding methods on the same types need pointer receivers.
5. **A committed document keeps pointing at the revision that produced it**: nothing rewrites the modeline, so a manifest maintained across releases is edited against the rules of the build that first exported it until someone re-imports or edits the line.

### Mitigations

- The two statements of the catalog prerequisite are adjacent in `parse.go`, so a change to either appears beside the other rather than in a file the author is not reading.
- `doc/cmd/infra.md` says the schema is a weaker check than `infra validate` and not a replacement for it, so a document an editor reports as clean is not mistaken for a validated one.
- The committed schema is never hand-edited: the test that fails on a discrepancy is the same code that repairs it, so the response to a failure is to run it rather than to patch JSON into agreement.
- `infra import` emits the optional spec fields with `omitempty`, so an exported document never contains the explicit null the schema rejects; only a hand-written one can reach it.
- The modeline is a YAML comment, so a document carrying one parses identically for anything that does not know the convention, and the stale-ref case costs editing help rather than correctness.

## Implementation Notes

The enum values were lifted onto their types as a change of its own, before anything read them, so the commit that introduced the schema changed no decoding behaviour. `UnmarshalYAML` reads the same `allowedValues()` the new `JSONSchema()` reads, which is what makes the schema's enum and the decoder's enum the same list rather than two lists that happen to match.

Three reflector settings are chosen rather than defaulted. Field names come from the `yaml` tags, because the types carry no `json` tags and the default would name every property after its Go identifier. Required-ness is taken from explicit `jsonschema:"required"` tags rather than inferred from `omitempty`, because several optional fields deliberately omit `omitempty` so the emitter always writes them, and inference would publish those as demands. The generated `$id` is suppressed, because it would be this package's Go import path, which is neither where the schema is published nor resolvable.

Only the document header and the metadata are marked required on a `Repository`, and only `description`, `ref` and `cron` on a schedule. A document carrying no `spec` parses, and a schedule may omit `cron_timezone` and `active` because `UnmarshalYAML` supplies a default for either, so demanding any of them would make the schema reject what the parser accepts.

Verification worth pinning: the committed file matches what the types produce, which the test asserts on every run; a document declaring `ci_catalog: true` without a description is reported by the schema and by `validate()` alike; a value outside an enum is reported against the same list the decoder would name; and `infra import` writes the modeline ahead of every document in a multi-project export, with the tagged ref for a stamped build and `refs/heads/main` for an un-stamped one.
